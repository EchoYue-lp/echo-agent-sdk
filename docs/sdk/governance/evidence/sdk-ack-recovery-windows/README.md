## Behavior and proof

1. A public `Run.replay(after=1)` returning retention gap `2..5`, snapshot `5`, and event `6` establishes a recovery connection from request cursor `1` to snapshot `5`. Fetching alone changes neither consumption nor live sequence. Only a successful official ACP ACK of the snapshot or returned event advances consumption and prunes queued events. Missing interior cursor `3` remains unobserved. A previously fetched empty page at cursor `5` cannot absorb and erase the later gap connection. Three language tests use the official ACP connection/session for the public replay request, response validation, and controlled notification completion.
2. When replay-covered ACK `10` is pending, the peer may already continue with gap `11..12`. Python and Java now admit only the contiguous next fact supported by that pending submission. Pending state never commits consumption, retires queues, closes EOF, authorizes arbitrary gaps, or permits a backward/overlapping gap. A failure keeps the received fact and buffered prefix; success commits only its submitted cursor. An empty after-gap page cannot authorize an absent cursor.
3. The additional three-language real-Host scenario runs the existing shared oversized-event model and byte-preserving Host proxy. An official native ACK is actually sent to the immutable Host; only its completion signal is held. The real Host receives the ACK and publishes its next gap before that completion. Both success and failure permutations exercise each production incoming-notification path, with no private feed call standing in for the Host. Java installs a typed `AcpClientTransport` delegate on the genuine `AcpClientSession`, delegating real stdio I/O; TypeScript/Python gate completion after the genuine official notification method. Six `*-pending-gap-*.json` records retain replay, raw Host notifications, resumed gap, and delivered projection.
