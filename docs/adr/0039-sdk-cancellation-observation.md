# ADR 0039: SDK cancellation observation preserves the original owner

- Date: 2026-10-16

## Status

Accepted for implementation; Host pins published framework9886502c83d6b1f6fa9212eb221db0e5874deaee. Complete runtime validation remains pending.
- Design: [SDK cancellation observation adapter](../supreme/specs/sdk-cancellation-observation/design.md).

## Context

Framework ADR0088 defines ExecutionNotSettled as observation knowledge rather than physical settlement. Existing SDK callback, Factory, Subagent and facade consumers could classify it as failure or release resources when only a local observer ended. A real old-Host Factory setup counter returned the original contextual observation while its same-child process remained alive; AgentClose was called prematurely. This counter is a specific before result, not proof of all Run terminal or recovery paths.

## Decision

Extend the existing Host owners and lossless error boundary under ADR0034. Reuse framework execution/claim/terminal authority and original SDK handles, callback leases, Factory Arc and producer collectors. Emit existing framework_error/Never details with exact observation/run/execution identity. Malformed observation validation errors cannot erase physical uncertainty. No matching original closure or authoritative fence means retained ownership and capacity, with no replacement execution.

Use the required controller hook only to delegate the original exact request CAS. Internal Task ownership waits through execute_to_settlement, never by re-executing. Fixed-Item Tool/Sandbox streams retain and drain their original owner instead of manufacturing a failure or EOF. The detailed design defines legitimate late-closure versus unrecoverable-unknown exits.

## Alternatives and consequences

Grace-triggered abort and default Failed reproduce the bug; a second registry/status/store would duplicate authority. Neither is adopted. The original B observation slice preserves existing wire routes and accepted membership; approved fallible Rust signature digests are regenerated by the sole producer after an exact published framework pin. It introduces no new language method, terminal kind or observation wire variant. The separately accepted A addition below has one explicit capability and one reverse operation; it does not turn the full Rust inventory into a language contract.

Non-cooperative or unknown physical work may retain existing capacity indefinitely. This truth is preferable to overlapping effects. Source preparation does not prove runtime repair: strong before/after, exact-source Host and language gates, independent review and final main acceptance remain required. Detailed scenarios, source migration and rollback are maintained only in the linked design.

## Accepted A: protect the original Workflow claim before effects

On 2026-10-16 the user chose A, “保留能力并实施保护合同（推荐）”, bound to the [reviewed proposal and preserved historical text](../sdk/governance/workflow-protected-claim-proposal.md). Framework Graph and its bound CheckpointStore remain the sole claim, protection and settlement authority. SDK adds only `protected_claim_v1` and `workflow_checkpoint_protect_claim({checkpoint_id, attempt_id}) -> Unit` to the existing reverse component call. A Rust/Host-only Graph capability getter projects its bound Store; it creates no language query API.

Legacy/false-capability Stores can still register and perform unrelated operations. Any possibly-node-executing claim-backed Approved/Modified resume, including a branch's new execution, requires capability before claim, fork save or effects; missing support returns existing `feature_unavailable/Never`. Deferred, Rejected without node execution, fresh run and ordinary physically finished error policies retain their specified paths. Only the original Store implements exact-attempt protection and destructive CRUD refusal; Host must not duplicate this algorithm or infer capability from the latest registration.

The accepted tradeoff is that a protected unknown owner can block indefinitely, even after a crash before effects started. Memory protection lasts within that Store instance; File and declared durable providers preserve it across restart. No force unlock, receipt query or automatic re-execution is added. Protected data must not be exposed to old binaries: old read/expiry paths may fail closed, but old delete/clear can still remove it. User approval establishes the contract, not runtime correctness; before/after and current-source validation are pending.
